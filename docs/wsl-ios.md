# iOS development on Windows with WSL

CapMac's experimental WSL backend builds and signs iPhone applications on Windows, then installs and launches them on a directly connected iPhone. It runs Linux compilers and CocoaPods inside WSL. It does not invoke xtool or connect to a Mac.

For **CocoaPods projects**, CapMac uses the application's original native code and the dependency graph generated by a real `pod install`. This path supports Swift, Objective-C, C and C++ sources, transitive pods, source and binary frameworks, resource bundles, build settings, install hooks, build scripts, and profile-authorized application entitlements. There is no artificial Capacitor 8 version requirement on this path; compatibility depends on the project's actual native inputs and toolchain.

CapMac creates a writable copy of the workspace under `.capmac/wsl/pods-inputs`, runs the installed Capacitor CLI there to sync plugins and web assets, and installs pods inside that copy. Your source `ios` directory, installed packages, Podfile, and lockfile are not rewritten. The copied lockfile guides CocoaPods' normal version resolution. Repeated builds reuse the isolated pod sandbox.

For **SPM projects**, CapMac imports the original Xcode application and extension targets. Linux Swift evaluates each `Package.swift`; remote sources use the exact revisions in `Package.resolved`, and binary XCFramework archives must match their manifest checksums. Local plugins, transitive Swift/Objective-C/C/C++ targets, and package resources remain part of the graph. CapMac does not replace your application with a generated host or impose a Capacitor 8 version requirement.

For **Flutter apps**, CapMac builds the iOS app's Runner project the same way, after doing in WSL what Flutter's Xcode scripts do on a Mac (see [Flutter apps](#flutter-apps)).

For **React Native apps**, CapMac runs CocoaPods in WSL with React Native's prebuilt core, so only the app and its native modules compile (see [React Native apps](#react-native-apps)).

This remains an experimental build backend, not a guarantee that every Xcode feature or Capacitor plugin works. See the compatibility limits below before choosing it for a project.

## Start here

You need WSL 2, an iPhone and a paid [Apple Developer Program](https://developer.apple.com/programs/) membership (US$99 a year). A free Apple Account can't sign apps here yet, so setup would stop at the Apple sign-in

You can set up and build either in CapMac Studio or in PowerShell. Both run the same setup, save it in the same files, and share the project's choice of where it builds.

**In CapMac Studio:** open your app, click the Mac picker next to **Run** and choose **This PC (no Mac)**. Without a paired Mac, the workspace also offers **No Mac? Build on this PC instead**, and the first screen of a new Studio offers **No Mac? Build on this PC**. The setup screen opens; press **Start setup**. See [Building in CapMac Studio](#building-in-capmac-studio) below.

**In PowerShell:** open it in your app's folder and run:

```powershell
capmac wsl setup
capmac backend wsl
```

`capmac backend wsl` makes this project build on this PC from now on, for `capmac run`, `capmac dev`, `capmac build` and `capmac doctor` (and in CapMac Studio). `capmac backend` shows the current choice and `capmac backend mac` goes back to the Mac. To choose for one command only, add `--backend mac` or `--backend wsl`. An Electron app always runs on the Mac.

Setup does everything in one run:

1. **Build tools.** It creates a separate `CapMac-Ubuntu` WSL distribution (your own distributions are untouched) and installs Swift 6.3.3 (signature-checked), the linker, the code signer, CocoaPods and the asset/storyboard compilers inside it. On Windows it also brings its own Python for the iPhone tools: python.org's 3.13 build (checksum-checked) with [pymobiledevice3](https://github.com/doronz88/pymobiledevice3), in `%LOCALAPPDATA%\CapMac\device-tools`, so there is no Python to install and yours is not touched. On a new PC this is the longest step, and it needs no sign-in.
2. **iPhone connection.** Windows talks to an iPhone over USB through Apple's own device server. If the Apple Devices app is missing, setup offers to install it from the Microsoft Store, then starts its device server in the background without opening a window. After the first run over the cable, the iPhone also runs over Wi-Fi (see [Connect the iPhone](#connect-the-iphone)).
3. **One Apple sign-in.** Setup first asks who does the Apple part:
   - **Let CapMac do it** (recommended). CapMac opens Apple's website in your default browser when it is Chromium-based (Edge, Chrome, Brave, Vivaldi), else in Edge, on a profile of its own under `%LOCALAPPDATA%\CapMac\AppleWeb`, apart from your everyday one. You sign in there the way you always sign in to Apple (CapMac never sees the password or the code); the dialog closes by itself once you are in, and CapMac closes the window. Everything after that happens without a window: CapMac's Apple session is made from that browser's sign-in, and what Apple makes only on its website for some accounts (certificates, profiles, new iPhones: its API answers HTTP 421) is made there, in a hidden copy of the browser. The sign-in is kept, protected for your Windows user, so later setups need no sign-in at all. **Restart** in the waiting dialog, or "with a fresh sign-in" in the choice, forgets it and opens a clean window. Closing the window stops setup. If a step on the website fails, the dialog says why and offers another try or doing it by hand, and CapMac keeps notes and a picture of Apple's page (never its sign-in page) in `AppleWeb\last-attempt`.
   - **Do it myself.** Enter your Apple Account email and password, then the two-factor code, in the terminal or in CapMac Studio's dialogs; they are kept in memory only. When Apple won't make the certificate for this sign-in, you make it on Apple's website from the request CapMac saves in Downloads, and CapMac picks the certificate up from there.

   If you belong to several developer teams, you pick one. The sign-in covers:
   - **Signing**, like Xcode's "Automatically manage signing". Setup reads your app and its extensions (such as widgets) from the Xcode project, shows the account changes it is about to make, and asks first: a development certificate for this PC, missing App IDs, capabilities such as Push Notifications or App Groups, and a plugged-in iPhone the team does not know yet. Nothing is removed or revoked. The certificate is kept in `%LOCALAPPDATA%\CapMac\Signing\<team>`, with its password protected for your Windows user, so builds never ask for it; its private key never leaves this PC. A certificate Apple already made from CapMac's request (say, in an earlier run) is found and used without asking again.
   - **Xcode 26.6**, downloaded from Apple's developer site (about 2.3 GB; an interrupted download continues on the next run), granted the way Apple's downloads page grants it. Only the iPhone SDK, the Swift resources and Apple's compiler runtime are taken from it.
4. **Next:** `capmac wsl doctor` to check everything, then `capmac wsl run` with your iPhone plugged in (or, after its first run, on the same Wi-Fi).

Run `capmac wsl setup --apple-login` to sign in again, for example after adding a plugin that needs a new capability. If setup stops, `.capmac/wsl/setup-status.json` records the step, without any account data.

Xcode and Linux Swift are a matched pair: Swift has to read the module interfaces that Apple's compiler wrote. CapMac pins Xcode 26.6 with Swift 6.3.3 and replaces an SDK imported from another Xcode release. Swift's own `ld64.lld` is built without iOS support, so the linker is Ubuntu's `ld64.lld`.

Libraries that Apple's compiler built (prebuilt SDKs such as Google Mobile Ads) call Objective-C methods through `_objc_msgSend$<selector>` stubs that the linker makes. In a large app, `ld64.lld` 18 points many of those stubs at the wrong method name, and the app then stops at launch with "unrecognized selector". So when a link made such stubs, CapMac writes them itself, the way the compiler writes ordinary method calls, links again, and checks every stub before the app is signed; an app whose stubs would call the wrong method is never signed.

Xcode's archive keeps a linked file's contents at its first link only and gives the other links a placeholder of the same size; the SDK import fills those from the real copy. An SDK imported by an older CapMac is imported again by the next setup, from the Xcode download it kept.

`doctor` exits with status 1 when something is missing; scripts can use `capmac wsl doctor --json`. The same backend is reachable as `capmac doctor`, `capmac build`, `capmac run` or `capmac dev` once `capmac backend wsl` picked it, or with `--backend wsl` on any of them. WSL commands never pair with a Mac or turn on the Mac command takeover.

### How the two-factor code is asked

`@expo/apple-utils` (the maintained Apple sign-in CapMac uses) asks for the two-factor code with its own terminal prompts, which live in a part of the package that can't be replaced. Its sign-in skips them when Apple's sign-in request succeeds. So while signing in, CapMac watches that request on the package's own HTTP client: when Apple answers that a code is needed, CapMac asks for it through its own prompts (the terminal, or Studio's dialogs), sends it to the same Apple endpoints the package would use, asks Apple to trust the session, and lets the sign-in continue. Every other request passes through untouched, and the watcher is removed when the sign-in ends.

## Building in CapMac Studio

Studio offers every option of `capmac wsl` and keeps the same settings.

| In Studio | Same as |
|---|---|
| Mac picker → **This PC (no Mac)**, or a Mac | `capmac backend wsl`, `capmac backend mac` |
| **Set up this PC…** → **Start setup** / **Continue setup** | `capmac wsl setup` |
| Setup screen → **Sign in to Apple again** | `capmac wsl setup --apple-login` |
| Setup screen → **Check this PC** | `capmac wsl doctor` |
| iPhone picker next to the Mac picker | `capmac wsl targets`, `--target <udid>` |
| **Run** | `capmac wsl run` |
| **Live** | `capmac wsl dev` |
| **Build IPA** (box icon) | `capmac wsl build` |
| More (…) → **Clean rebuild** | `--clean` |

The setup screen shows each step: build tools, the iPhone connection, Apple sign-in, signing, the Xcode download and the iPhone SDK. While Xcode downloads it shows the gigabytes so far, and where a download that stopped earlier continued from. Questions come as dialogs: installing Apple Devices from the Microsoft Store, your Apple Account email, password and code, your team, and the list of signing changes to approve before anything in your account changes. You can close the screen while setup runs; a bar above the workspace shows the step, and **Show** opens it again.

When setup stops (a failed step, or you pressed **Stop setup**), the screen and the bar say at which step, from `.capmac/wsl/setup-status.json`. **Continue setup** starts again and skips what is already in place: the tools are checked rather than reinstalled, and an interrupted Xcode download continues.

**Run** before setup is complete opens the setup screen instead. Once it is set up, plug in your iPhone, unlock it and press **Run**: the timeline shows the web build, the native project, the build and signing, the install and the launch, and the app's native logs stream into the console. With several iPhones plugged in, pick one in the iPhone picker. **Live** starts your dev server and a relay on this PC's network, so keep the iPhone on the same network. **Build IPA** saves a signed development `.ipa` and shows where it is.

## Use your own tools instead (advanced)

You can skip the managed setup and point CapMac at tools and signing files you already have. `capmac wsl setup` with explicit paths saves them to the project's private `.capmac/wsl.json`; run outside an interactive terminal, it only saves paths and prints this guide.

1. Install WSL 2 and Ubuntu. Microsoft's [WSL installation guide](https://learn.microsoft.com/en-us/windows/wsl/install) describes `wsl --install` and the first-run account setup. Choose your distribution with `--distro Ubuntu` if you have several installed.
2. Install Linux Swift, Clang, LLVM including `ld64.lld` and `llvm-ar`, `zsign`, Python 3, and OpenSSL in WSL. CocoaPods projects also need Ruby, CocoaPods, Git, libcurl, and rsync. Follow the [Swift Linux installation instructions](https://www.swift.org/install/linux/) for your distribution.
3. Provide your own iPhoneOS SDK and matching Darwin Swift modules/runtime resources. A stock Linux Swift compiler alone is not a complete iOS toolchain. CapMac checks a real iOS compilation and link before declaring the compiler ready.
4. Provide an Apple development signing certificate with its private key in a `.p12` file and a `.mobileprovision` profile matching your application's bundle ID and your iPhone, or let the managed setup above make them.

CapMac does not ship Apple's SDK. The managed setup downloads Xcode from Apple with your own Apple Account; obtain and use the SDK and signing material under the terms that apply to your use.

The open-source linker and signing tools can be prepared inside Ubuntu as follows. The signer is pinned to the revision whose password-input behavior CapMac uses ([zsign build file](https://github.com/zhlynn/zsign/blob/614caa8d1ca949e260e5746144aa52d27a4b08d6/build/linux/Makefile)):

```bash
sudo apt-get update
sudo apt-get install -y git ca-certificates build-essential pkg-config libssl-dev python3 openssl clang llvm lld ruby-dev libcurl4t64 rsync
gem install --user-install cocoapods --no-document
export PATH="$(ruby -r rubygems -e 'puts Gem.user_dir')/bin:$PATH"
git clone https://github.com/zhlynn/zsign.git
git -C zsign checkout --detach 614caa8d1ca949e260e5746144aa52d27a4b08d6
make -C zsign/build/linux
sudo install -m 755 zsign/bin/zsign /usr/local/bin/zsign
```

The package names above target Ubuntu 24.04; older distributions may call the curl runtime package `libcurl4`. Add the Ruby gem executable directory to your WSL shell's `PATH` permanently, or select `pod` with `--pod /absolute/path/to/pod`. Keep the Ruby and CocoaPods installations compatible. If your project has a Gemfile, install its gems in WSL with `bundle install`; CapMac uses `bundle exec pod` and the pinned Gemfile.lock unless you explicitly supply `--pod`.

Choose a Linux Swift release matching the Swift version of the Apple toolchain supplying your SDK and resources. In an extracted Xcode distribution, the relevant directories are:

```text
Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk
Xcode.app/Contents/Developer/Toolchains/XcodeDefault.xctoolchain/usr/lib/swift
```

Use the first directory for `--sdk`. CapMac finds the Swift resources automatically when the SDK retains this standard directory layout; use `--swift-resources` with the second directory if you keep the SDK separately. The extracted Apple compiler executables are macOS programs; install and select a Linux Swift compiler separately.

CapMac prepares a cached resource overlay combining the supplied Apple Swift resources with the Linux compiler's Clang headers. It does not modify the supplied SDK or Swift resources. There is no validated universal Swift/SDK version pair bundled with CapMac. The doctor's UIKit and WebKit compile-and-link check is required before attempting an application build.

Use explicit paths when tools are not on WSL's `PATH`:

```powershell
capmac wsl setup --distro Ubuntu `
  --sdk /opt/apple/iPhoneOS.sdk `
  --swift /opt/swift/usr/bin/swiftc `
  --swift-resources /opt/apple/swift `
  --linker /usr/bin/ld64.lld `
  --clang /usr/bin/clang `
  --archive /usr/bin/llvm-ar `
  --signer /usr/local/bin/zsign `
  --certificate C:\Signing\Development.p12 `
  --profile C:\Signing\Development.mobileprovision
```

For CocoaPods projects, install the resource tools once after installing Linux Swift:

```powershell
capmac wsl setup --install-resources
capmac wsl doctor
```

This requires Linux Swift 6.2 or newer to build the standalone asset compiler and installs storyboard/XIB, Core Data, and string-catalog helpers from [omarchy-apple-dev](https://github.com/joshuaswarren/omarchy-apple-dev/tree/66a11a37dfc0bfb755d04bde1ecbeedc17753b3b), pinned to revision `66a11a37dfc0bfb755d04bde1ecbeedc17753b3b`. CapMac applies a verified patch for standard Capacitor storyboard scenes. These helpers are MIT licensed; the installation retains their license and source attribution under the WSL user's `.local/share/capmac/resource-tools` directory. Only the standalone resource helpers are installed; xtool is not a dependency. Use `--actool`, `--ibtool`, `--momc`, and `--xcstrings` to select other compatible Linux implementations.

These settings are remembered, so subsequent builds need no repeated path flags. Compiler, linker, signing-tool, and Swift resource paths refer to files inside WSL. The SDK can also be supplied as a Windows absolute path. `--python` selects Python on Windows for communication with the iPhone. Keep certificates and profiles outside your repository. For unattended builds, use `--password-env YOUR_SECRET_VARIABLE`; the value is read from the Windows environment. The default password variable is `CAPMAC_IOS_PASSWORD`. Do not put a certificate password in a command argument or in project configuration. Interactive builds can ask for the password without echoing it.

CI can supply the SDK, certificate, and profile through `CAPMAC_IOS_SDK`, `CAPMAC_IOS_CERTIFICATE`, and `CAPMAC_IOS_PROFILE` instead of saving machine paths in the project.

## Connect the iPhone

Connect the iPhone directly to Windows. Install Apple's USB drivers through Apple Devices, unlock the iPhone, trust the development computer, and enable Developer Mode when iOS requests it. Device communication runs on Windows; USB passthrough to WSL is not required. Setup installs the device tools ([pymobiledevice3](https://github.com/doronz88/pymobiledevice3) 11.32.0) in CapMac's own Python; to use your own Python with pymobiledevice3 instead, pass `--python C:\Path\To\python.exe` to setup. List the iPhones CapMac can reach, and how:

```powershell
capmac wsl targets
```

For iOS 17.4 and newer, CapMac opens apps through pymobiledevice3's userspace tunnel, which needs no administrator rights. While the iPhone is locked, iOS opens no apps: the run waits and says "Unlock your iPhone to open the app", however long it takes (Stop ends the wait).

From iOS 16, the iPhone opens the apps CapMac installs only with **Developer Mode** on (Settings › Privacy & Security › Developer Mode; the iPhone restarts, then asks to turn it on). CapMac reads it over the cable: Studio's iPhone picker says "Developer Mode off" and the iPhone pane lists the steps, and `capmac wsl targets` prints them. iOS hides that switch until a developer tool asks, so CapMac shows it in Settings when it finds Developer Mode off. A run warns at the start, builds and installs anyway, and at "Open app" waits until Developer Mode is on, through the restart (Stop ends the wait). An iPhone that doesn't trust the PC yet shows as "Not trusted".

### Over Wi-Fi

After the first run over the cable, the iPhone also runs over Wi-Fi, with no cable, when it and the PC are on the same network. In that first run, after installing, CapMac pairs the iPhone for Wi-Fi over the trusted cable (RemotePairing, as Xcode does; there is no prompt on the iPhone), and the run says so. Unplugged, the iPhone then shows as "Connected · Wi-Fi" in Studio and as `Wi-Fi` in `capmac wsl targets`, and `capmac wsl run` installs, opens, logs and stops the app over Wi-Fi through the same no-administrator tunnel. An asleep iPhone leaves the network: a run waits up to five minutes for it ("Unlock your iPhone to install the app") and goes on once it is unlocked. If Windows asks whether Python may use the network, allow it on private networks; CapMac finds the iPhone with mDNS. Wi-Fi needs iOS 17 or later.

iOS 17.0–17.3 requires a tunnel service started separately from an administrator PowerShell prompt:

```powershell
& "$env:LOCALAPPDATA\CapMac\device-tools\11.32.0-python-3.13.16\python.exe" -I -m pymobiledevice3 remote tunneld
```

Leave that service running while CapMac launches the app. CapMac does not elevate itself. The [pymobiledevice3 documentation](https://github.com/doronz88/pymobiledevice3) covers device services and pairing; CapMac includes actionable hints when these prerequisites fail.

## Build, run, and edit

Once the doctor passes, use your saved settings to build or run:

```powershell
capmac wsl build
capmac wsl run
```

`build` prints the application and IPA paths. `run` builds, signs, installs, and launches on a physical iPhone. Select one of several devices with `--target YOUR_DEVICE_UDID`, or use `--no-logs` to return after launch. Each build compiles in a fresh folder; `--clean` also removes the prepared native project (`.capmac/wsl/pods-inputs` or `xcode-inputs`) and the compilers' module cache in WSL first. Downloaded Swift packages are kept.

For CocoaPods projects, each build syncs the isolated application, resolves dependencies using CocoaPods, and compiles the resulting native targets in dependency order. The application retains its native delegates and initialization code. App icons, supported storyboards/XIBs, localization, string catalogs, Core Data models, and privacy manifests are processed through the configured resource tools. Application entitlements must be granted by the supplied provisioning profile.

Use `--configuration Staging` for an existing custom configuration and `--scheme App` to select the application target when needed. Podfile install hooks and native build scripts execute in WSL, so any tools they call must also be available there. If a hook queries Xcode's version, retain the extracted `Xcode.app/Contents/version.plist` or supply the actual matching value using `--xcode-version`; this supplies version metadata, not an Xcode build service.

For SPM projects, commit a complete `Package.resolved` before building. CapMac does not resolve newer versions to repair missing pins or unavailable binary archives. A deleted upstream binary needs the original archive with its expected checksum, placed in WSL at `~/.cache/capmac/swift-packages/archives/<sha256>.zip`, or an explicit dependency update in your project. A Mac that built the project before often still has it in `~/Library/Caches/org.swift.swiftpm/artifacts`. Swift package build-tool plugins, macros, and module aliases currently fail with a diagnostic when their additional build behavior is required.

Each app extension requires its own provisioning profile, selected by bundle ID with `--extension-profile com.example.app.widget=C:\Signing\Widget.mobileprovision`. CapMac packages and signs imported extension targets with the application; the supplied profiles must authorize their entitlements and shared app groups.

For live development, use one command:

```powershell
capmac dev --backend wsl
```

CapMac starts your project's dev server, creates a LAN relay for web requests and HMR WebSockets, builds the development app, and launches it on your iPhone. Keep the phone and PC on the same reachable network and allow the relay through Windows Firewall when prompted. The dev server can stay bound to `localhost`.

If your dev server is already running, point CapMac at its local URL:

```powershell
capmac wsl dev --url http://localhost:5173
```

Use `--live-host YOUR_PC_ADDRESS` if automatic address selection picks the wrong network adapter. Web edits follow the dev server's normal reload behavior. Supported native or configuration edits trigger a rebuild and reinstall automatically; pass `--no-watch` to disable that. Adding a plugin still needs its usual package installation before rebuilding.

The live URL and local-network settings are applied to the isolated development app. Your source Capacitor configuration stays suitable for packaged builds. Stop the session with Ctrl+C.

## Flutter apps

A Flutter app's iOS app builds on this PC with the same setup and the same commands:

```powershell
cd my_flutter_app
capmac wsl setup        # signing for the app's bundle ID, once
capmac backend wsl
capmac run              # release build on the iPhone plugged into this PC
capmac run --mode profile
capmac dev              # rebuilds and reopens the app each time you save
```

The first build gets three things into CapMac's WSL distro and keeps them for later builds:

- Flutter's Linux release of the version your project uses (the one it pins with FVM or `capmac.json`, else this PC's, else the latest stable), from Flutter's own archive, checked against Flutter's published SHA-256.
- Dart's iPhone compiler (`gen_snapshot`). Google ships it only for Macs, so CapMac builds it from Dart's source at the revision Flutter's engine pins. It takes about 5 minutes, once per Dart version. The build uses Apple's `qsort`, so the compiler makes byte-for-byte the same app code as Flutter's on a Mac.
- Flutter's iPhone engine (`Flutter.xcframework`) for the build mode, from Google's download.

Each build then works in a copy of the project in WSL (`~/.cache/capmac/flutter-builds`), leaving your source folder as it is:

1. `flutter pub get`, then the files Flutter writes only on a Mac: `ios/Flutter/Generated.xcconfig` and the plugins' Swift packages (`FlutterGeneratedPluginSwiftPackage`).
2. Flutter compiles the Dart code to kernel and makes the asset bundle, with unused icons left out of the icon font. The shaders are compiled for Metal, as on a Mac.
3. Dart's iPhone compiler makes `App.framework`, next to Google's `Flutter.framework`.
4. The Runner project is imported without Flutter's two Xcode scripts, whose work is done, then compiled, signed and packaged like any app.

On a real iPhone, a Flutter app runs release or profile builds here. Debug builds need Xcode's debugger to run on an iPhone, so hot reload stays with a paired Mac. `capmac dev` here rebuilds the app and opens it again on every save. The app's `print` lines show in the console as Dart output.

Plugins must come as Swift packages, which Flutter uses by default. A plugin that has only a CocoaPods podspec stops the build with its name: update it, or build the app on a Mac.

## React Native apps

A React Native app's iOS app builds on this PC with the same setup and commands:

```powershell
cd my-react-native-app
capmac wsl setup             # signing for the app's bundle ID, once
capmac wsl build --unsigned  # check that it builds, without signing
capmac backend wsl
capmac run
```

What a Mac's `pod install` and Xcode do, CapMac does in WSL:

- React Native's Podfile and build scripts run Node.js, so CapMac puts Node.js in its WSL distro once, from nodejs.org, checked against its published SHA-256.
- CocoaPods resolves the app's native libraries with React Native's prebuilt core (`RCT_USE_PREBUILT_RNCORE` and `RCT_USE_RN_DEP`): React and its dependencies come as frameworks from React Native's own release on Maven, so only the app and its native modules compile. The sample's first build takes about 2 minutes for `pod install` and 2 for compiling.
- The Pods folder lives on WSL's own disk, which is far faster than the Windows disk for its thousands of files, and is mounted into the build's workspace.
- `pod install` runs again only when something it reads changes: the Podfile and its lock, the app's Xcode project, the packages' lockfile and patches, and your workspace's own packages. Otherwise the next build reuses its result in about a second.
- A release build carries the JavaScript, which Metro bundles and Hermes compiles on this PC.

The build's files stay outside your project, in `%LOCALAPPDATA%\CapMac\wsl-builds\<project>`, because Metro watches the project's folder.
`capmac wsl build --clean` starts over, Pods included.

React Native's template launch screen uses a bold system font, which the Linux storyboard compiler can't build yet.
The app then gets a plain launch screen instead (`UILaunchScreen` in its Info.plist), and the build says so.

## Compatibility limits

CocoaPods support means using CocoaPods' real resolver and generated projects; it does not reproduce every Apple build tool. The portable resource compilers support specific resource features. Unsupported assets or Interface Builder features fail with diagnostics rather than being silently omitted, with one exception: a launch screen the storyboard compiler can't build becomes a plain one, and the build says so. App icon sizes listed without an image are left out, as Xcode does. Metal shader sources, Core ML model/package compilation, Core Data mapping models, and Rez phases currently need additional compiler support. Objective-C Core Data automatic class generation needs manual classes or a compatible generator.

Application extensions are imported; other unsupported product types are rejected. Scripts and pod `prepare_command` hooks that require macOS executables or unavailable Linux tools need a Linux-compatible implementation. Build phases are not skipped to make a build appear successful. Existing custom native code is preserved, but it still has to compile with the supplied cross-compilation toolchain.

Importing arbitrary native projects as a separate project type, and iOS simulators, remain future work. Flutter plugins that have only CocoaPods podspecs need a Mac. The existing Mac backend remains available for projects that depend on Xcode-only behavior.

## What validation means

Passing the doctor proves that the configured tools can compile and link its small iOS probe. For CocoaPods it also checks Ruby, Git, CocoaPods, the Xcode project parser, libcurl loading, and native resource-tool availability. It does not prove that every plugin or Apple framework is compatible.

The automated Linux integration fixture exercises actual CocoaPods dependency resolution and project export with mixed Swift/Objective-C/C++ pods, transitive dependencies, resources, install hooks, and lockfile preservation. It does not compile an iPhone executable. With a disposable Ruby container that has CocoaPods, Git, Python, and libcurl installed, maintainers can run it with `CAPMAC_PODS_TEST_CONTAINER=<container-name>` and `npx vitest run test/unit/wsl-cocoapods.test.ts`.

The Swift package integration test evaluates real manifests with Linux Swift and checks transitive C/Swift targets, build conditions, resource accessors, and preserved application/extension targets. On Windows, enable it with `CAPMAC_SWIFT_TEST_DISTRO=<distribution>` and `CAPMAC_SWIFT_TEST_EXECUTABLE=/absolute/path/to/swift`, then run `npx vitest run test/unit/wsl-swift-packages.test.ts`. This verifies import behavior rather than an iOS executable.

Resource tests compile the standard Capacitor main and launch storyboards and inspect their binary nib archives. After installing the example application's npm dependencies, `CAPMAC_TEST_CAPACITOR_SYNC=1` enables `test/unit/wsl-cocoapods-sync.test.ts`, which runs the installed Capacitor CLI with both a Capacitor plugin and a Cordova Objective-C plugin in a disposable project.

A signed app successfully running on a real iPhone is the final device check. SDK-specific application compilation, signing, and real-device validation remain pending until the required SDK and signing material are supplied. Treat this backend as experimental until that check passes with your toolchain, account, device, and application.
